# ── dtc_components, zuschaltbar seit MF-1100 ──────────────────────────
#
# Vier von zehn Modulen des uebernommenen Fremdbestands
# (src/dtc_components/, MF-1099) haben keinen Aufrufer. Das ist KEINE
# Formalie, sondern der aufschlussreichste Befund der Verdrahtung:
#
#   Aufgerufen von der mitgelieferten Testreihe (6):
#     bitbuffer.c  crc.c  encoding.c  flux.c  detect.c  ctraw.c
#   NICHT aufgerufen, also ungeprueft (4):
#     ipf.c  match.c  protection.c  track.c
#
# Uebersetzt auf die zugesagten Faehigkeiten heisst das: CRC, FM/MFM,
# GCR, Bitpuffer, Flussstatistik, Formaterkennung und der CT-Raw-
# Rundlauf sind belegt — der IBM-MFM-Sektorkopf-Scanner, die
# Amiga-Sync-Erkennung, der Weak-Bit-Vergleich, das verschiebungs-
# tolerante Track-Matching, die Schutz-Heuristiken und die
# IPF-Chunk-Analyse sind es NICHT. Sie stehen im README des Pakets
# unter "Implemented", und die Testreihe fasst sie nicht an.
#
# Plan-Anker nach der Verwaisten-Regel (MF-621): sie bleiben, weil die
# Verdrahtung modulweise laeuft und die Orakel je Scheibe in
# docs/QUARANTINE.md benannt sind (MFM gegen den eigenen Encoder seit
# MF-938, IPF gegen die zwei SPS-Erhaltungsabbilder aus MF-1079). Ohne
# eigene Abnahme wird keines davon an einen Produktpfad gehaengt —
# genau das waere die Wette der fuenf fabrizierten Parser.
#
# NACHTRAG MF-1109 — die Abnahme ist gelaufen, und sie faellt fuer ALLE
# VIER negativ aus. Sie bleiben damit hier, und zwar nicht mehr als
# "noch nicht geprueft", sondern als "geprueft und nicht verwendbar":
#
#   track.c      `header_ok` rechnet die Kopf-CRC ab dem FE statt ab den
#                drei A1. Gemessen an einem spezifikationsgerechten
#                Adressfeld: Rest ueber A1 A1 A1 FE C H R N CRC = 0x0000,
#                ab FE = 0x90DC — das Pruefbit meldet zuverlaessig 0
#                (Klasse MF-1000). Dazu traegt `data_crc` einen
#                Zwischenwert ueber FE C H R N, nicht die Daten-CRC.
#   match.c      `dtc_track_match()` meldet bei leeren Bitfeldern Erfolg
#                (rc 0), laesst `compared_bits` UNGESCHRIEBEN (Giftmuster
#                0xCD ueberlebt) und liefert `differing_bits = SIZE_MAX`.
#   protection.c der Header zaehlt fuenf Schutzarten auf, die Funktion
#                setzt zwei. WEAK_BITS, VORPAL und VMAX sind ueber JEDE
#                Eingabe unerreichbar — die Tafeln liegen in encoding.c,
#                es fehlt die Verbindung.
#   ipf.c        die Block-CRC wird gelesen, nicht geprueft (0xDEADBEEF
#                geht durch); `id` wird unbedingt genullt. Und UFT hat
#                seit MF-1079 einen IPF-Leser auf T1 — das Modul ersetzt
#                nichts.
#
# Festgehalten von tests/test_dtc_ungeprueft.c (24 Zusagen), der die
# Dateien NICHT anfasst und bewusst NICHT an UFT_WITH_DTC_COMPONENTS
# haengt. Die Wege heraus stehen als P3-377.
#
# UND DESHALB STEHEN DIE VIER PFADE HIER NICHT MEHR — mit einer
# Einschraenkung, die groesser ist als der Eintrag selbst.
#
# Das Tor hat den MF-1109-Commit im ersten Anlauf ABGEWIESEN: "4
# Grundlinien-Eintraege treffen nicht mehr zu — das Modul hat inzwischen
# einen Aufrufer." Der Aufrufer ist der Abnahme-TEST. Produktiv
# erreichbar ist weiterhin KEINES der vier.
#
# Das ist der **vierte** Beleg fuer P3-223 in diesem Baum, nach
# `src/detect` (Phase 2), der `FloppyDevice`-Schicht (Phase 4d, dort
