# Grundlinie fuer scripts/audit_fdc_gaps.py (MF-838)
#
# Die Zahl unten ist die Anzahl der Eintraege in
# `include/uft/formats/uft_fdc_gaps.h`, die sich SELBST widersprechen —
# entweder passt ihr Spurlayout nicht auf ihre eigene `track_bytes`
# (Invariante PASSEN), oder ihr Format-Gap ist kleiner als ihr
# Lese/Schreib-Gap (Invariante ORDNUNG). Das Tor schlaegt an, wenn sie
# STEIGT.
#
# Stand 2026-09-03, nach MF-838: 17 Eintraege, 11 widerspruechlich.
#
# Warum 11 stehen bleiben und nicht behoben wurden:
#
#   Berichtigt wurde nur, was eine BENANNTE Quelle traegt — PC 1.44M
#   (Ch. Hochstaetter, FDFORMAT/88 1.8, ueber FreeDOS FORMAT 0.92
#   `floppy.c:952`). Fuer die uebrigen zehn Eintraege (BBC, PC-98,
#   Amstrad, MSX, 8-Zoll-FM, Atari) liegt keine Quelle vor.
#
#   Sie mit ABGELEITETEN Werten stimmig zu machen waere moeglich — die
#   Arithmetik gibt fuer jeden Eintrag ein passendes `gap4b` her — aber
#   es waere schlechter: die Eintraege wuerden konsistent, ohne richtig
#   zu werden, und der Widerspruch fiele nicht mehr auf. Sichtbar falsch
#   ist besser als unsichtbar falsch.
#
# Was die Zahl bereits erklaert:
#
#   Die PC-, MSX- und Amstrad-Eintraege liegen um 430 bzw. 186 Byte
#   darueber. Bei ihnen steht `gap4b = 664` — das ist der ATARI-ST-Wert
#   (60 + 9 x 614 = 5586; 6250 - 5586 = 664, siehe MF-828), fuer IBM
#   waeren es 234. Das bleibt eine Herleitung ohne Quelle.
#
# ── MF-940: die beiden Atari-Eintraege sind BEHOBEN (11 -> 9) ─────────
#
#   Hier stand: „Bei den Atari-Eintraegen ist der 60-Byte-Vorspann
#   DOPPELT gezaehlt (gap4a = 60 UND gap1 = 60), wo Brods
#   Write-Track-Tabelle nur einen nennt: ,Intro: 60 bytes of $4E'.
#   Beides ist eine Herleitung, keine Quelle — deshalb steht es hier
#   und nicht im Code."
#
#   Die Diagnose war richtig; es fehlte nur die Quelle. Sie liegt jetzt
#   vor: FastCopy III (Martin Backschat, Atari ST), Quelltext-Fassung
#   vom 5.2.1990, `FDC.S`, Unterprogramm `fdc_buildtrack`. Es schreibt am
#   Spuranfang UNMITTELBAR Gap1 — `moveq #60-1,d3` fuer 9 Sektoren, dann
#   `wbmult` mit Fuellbyte $4E; davor steht nichts. Ein gap4a existiert
#   im ST-Spurlayout nicht.
#
#   `gap4a = 0` laesst die Rechnung exakt aufgehen:
#       0 + 60 + 9 x (574 + 40) + 664 = 6250 = track_bytes
#
#   Dieselbe Quelle bestaetigt unabhaengig Gap1 = 60, post-IDAM = 22
#   (dort „Gap3.1") und post-Daten = 40 (dort „Gap4") — der Eintrag war
#   also bis auf gap4a richtig.
#
#   Lizenz: Freeware (FCOPYENG.TXT §3A) — Kopieren und Benutzen frei,
#   keine Aenderungs- oder Einbau-Erlaubnis. Uebernommen ist nichts; die
#   0 ist eine abgelesene Tatsache ueber das Spurlayout (Kanal „Spec"
#   nach MF-695). Der Quelltext gehoert NICHT ins Repository.
#
#   Stand danach: 17 Eintraege, 9 widerspruechlich.
#
# Grenze des Verfahrens: „passt" heisst nicht „stimmt". Das Tor prueft
# Selbstkonsistenz, nicht Richtigkeit.
#
# Senken ist erwuenscht, Heben braucht eine Begruendung im Commit.
#
# MF-1177: 9 -> 3. Sechs Eintraege haben neue Lueckenwerte bekommen, jeder
# mit einer benannten Quelle; drei bleiben widerspruechlich und sagen das
# jetzt selbst.
#
# Die Quelle ist keirf/greaseweazle, Commit
# 26690f89967d519e0106ab9566019a026b920bb4 (2026-03-18), **Unlicense** —
# „released into the public domain", also woertlich uebernehmbar.
# Gemessen in seinen 38 `diskdefs*.cfg`: 149 Definitionen, 86 mit `gap3`,
# 22 mit `cskew`, 7 mit `hskew`. NUR GELESEN; greaseweazle wurde nicht
# gebaut und nicht ausgefuehrt und ist deshalb nach der eigenen Regel von
# `docs/ORACLES.md` KEIN Oracle, sondern der Kanal *Spec/Daten* (MF-695).
#
# Was sich geaendert hat, je Eintrag mit seiner gw-Definition:
#   PC 360K   gap3 80 -> 84, gap4b 664 -> 182   `ibm.360`
#   PC 720K   gap3 80 -> 84, gap4b 664 -> 182   `ibm.720`
#   MSX 1DD   gap3 80 -> 84, gap4b 664 -> 182   `msx.1dd`
#   MSX 2DD   gap3 80 -> 84, gap4b 664 -> 182   `msx.2dd`
#   BBC ADFS  gap3 57 bleibt, gap4b 400 -> 104  `adfs.640`
#   PC-98 2HD gap3 116 bleibt, gap4b 600 -> 654 `pc98.2hd`
#
# `gap4b` ist dabei kein neuer Messwert, sondern der REST: greaseweazle
# hat gar kein solches Feld, weil der Vor-Index-Zwischenraum das ist, was
# nach Spurkopf, Sektoren und gap3 uebrig bleibt (MF-1169). Nur `gap3`
# kommt aus der Quelle.
#
# Die drei, die bleiben, und warum:
#   AMSTRAD_DATA / AMSTRAD_SYS  greaseweazle hat KEINE Amstrad-Datei; seine
#     ZX-Definitionen `3dos.ss40`/`3dos.ds80` tragen dieselbe Geometrie
#     (9 x 512, 250k) und nennen kein `gap3`. Beide Zeilen sind ausserdem
#     bis aufs Byte gleich, obwohl sich Data- und System-Format gerade im
#     gap3 unterscheiden — das Muster eines kopierten Blocks.
#   BBC_DFS  `gap3 = 21` UND `iam = no` sind belegt (`dfs.ss80`), aber
#     `gap4a = 40` / `gap1 = 26` sind IBM-Werte. Selbst ohne
#     Index-Adressmarke bleibt der Rest negativ (-41); zum Aufgehen
#     braeuchte es einen Spurkopf von etwa 16 Byte, und dafuer gibt es
#     hier keine Quelle.
#
# Seit MF-1177 traegt jedes Profil `gap_beleg` und `gap_quelle`, und
# `tests/test_fdc_profil_verdrahtet.c` verlangt: BELEGT muss aufgehen,
# UNBELEGT/TEILBELEGT darf NICHT aufgehen, und eine Angabe muss immer
# dastehen. Ein Widerspruch ist damit erlaubt — ein Widerspruch ohne
# Begruendung nicht.
#
# ZWEITE GRENZE, neu gemessen und wichtiger als die Zahl: dieses Tor
# rechnet `gap4a + gap1 + sectors x (satz + gap3) + gap4b` und laesst die
# Index-Adressmarke AUS. `uft_fdc_calc_gap3()` zaehlt sie MIT (fest 146
# bzw. 73). Dass PC 1.44M hier „mit 16 Byte Luft passte", war kein
# Spielraum, sondern genau die nicht gezaehlte IAM. Die eine Rechnung
# steht seit MF-1177 in `uft_fdc_gap_space()`, das den PROFILEIGENEN
# Spurkopf samt `iam`-Angabe nimmt.
